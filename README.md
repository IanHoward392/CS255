# CS255
Project Reflection

Summary: The client was Liam, founder of DriverPass, a new driving school. He needed a system for customers to register for lesson packages, schedule appointments, and complete online coursework, plus admin tools for his secretary, IT officer, and himself to manage accounts, packages, and activity reports.

What I Did Well: I turned a pretty casual interview into specific, concrete requirements instead of vague ones, like the exact packages, two-hour appointment blocks, and the 10-car fleet limit. My diagrams also stayed consistent with each other from the use case diagram through the class diagram.

What I Would Revise: My class diagram. The relationships between classes like Employee, ActivityLog, and Appointment work, but I think they could be simplified or thought through a bit more carefully.

Interpreting User Needs: I kept going back to the interview transcript instead of guessing, so requirements like the customer self-service password reset came directly from what Liam said, not assumptions on my part. This matters because the system is built for the client, not for me, so ignoring their actual needs makes for a bad design no matter how polished it looks.

My Approach: I start broad and narrow down, reading the requirements until I actually understand the problem before sketching out the big pieces. Going forward, I want to bring in diagrams earlier in the process, even rough ones, since they force you to catch edge cases before you're deep into documentation.
